# OmniDerm — data-flow audit

AUDIT BASIS: /Users/sbkoth/work/Omni/OmniDerm — docs/REGULATORY.md, ISSUES.md (both 2026-08-08), Info.plist (root), OmniDerm.entitlements, PrivacyInfo.xcprivacy, Package.swift/Package.resolved, and a full grep of the Swift sources.

WHAT THE CODE ACTUALLY SHOWS

1) No accounts, no Prameya server. There is no login code anywhere. No AuthenticationServices/ASAuthorization import, no StoreKit, no MetricKit, no analytics SDK, no ad SDK. Dependencies are exactly: mlx-swift, mlx-swift-lm, swift-huggingface, swift-transformers, swift-jinja, EventSource, plus Apple SPM packages. Prameya operates no backend that receives user content and holds no user-profile database. Sign in with Apple appears ONLY in the stray /OmniDent.entitlements (a different app's file — ISSUES.md DERM-034); OmniDerm.entitlements has no applesignin key.

2) Network egress — exactly one non-Apple destination. Domain/MLX/Download/{RobustDownloader,HubDownloaderBridge,ResilientResolve}.swift use HubClient from huggingface/swift-huggingface 0.9.0 to fetch MLX model weights. Package.swift line 17-18 confirms the huggingface packages. Info.plist sets NSAppTransportSecurity NSAllowsArbitraryLoads=false, so HTTPS only. ISSUES.md DERM-051 states plainly: "Model download is the app's only network activity." The catalog (App/OmniDermCatalog.swift) ships two models: Qwen3 0.6B 4-bit (~420 MB, text) and mlx-community/Qwen2-VL-2B-Instruct-4bit (~1.2 GB, vision). Policy is MLXModelPolicy.unrestricted — i.e. NO size/cellular consent gate today (DERM-050). The "no networking / nothing leaves the device" claim in the shipped UI copy is therefore false as written.

3) Photos. Intake is PhotosUI/PhotosPicker in Features/Learn/LearnView.swift (PhotoSelfCheckEducationView), holding the image as `selectedImageData: Data?` in SwiftUI @State. Domain/MLX/AnalysisImage.swift keeps decoded CGImages in a bounded in-memory NSCache (64 MB cost limit, 12-entry cap, clearCache() on memory/thermal pressure). NOTHING writes photos to SwiftData, to disk, or to CloudKit — I found no persistence path for images at all. So photos are memory-resident only, for the life of the screen. NOTE: Info.plist declares NSCameraUsageDescription but there is NO AVCapture/AVFoundation/UIImagePicker code anywhere — the camera permission string is declared for a capture path that does not exist. Images come from the photo library only.

4) The clinical/diagnostic loop. PhotoSelfCheckEducationView sends the photo to a local Qwen2-VL prompt that produces ABCDE observations. REGULATORY.md §1 and ISSUES.md DERM-002 call this the single highest-severity item (FDA device jurisdiction under 21 U.S.C. §360j(o)(1)(E), Apple 1.4.1, FTC MelApp 132 3211 / Mole Detective 132 3210). I could NOT find any FDA-clearance feature gate in the code. Domain/Core/Claims/DermClaimsGate.swift is a copy/claims LINTER (it flags strings like "point your camera at", "scan your mole"), not a runtime feature switch. The default-OFF clearance gate described in the wave-2 brief does not exist in the tree I read — the policy is written to the post-wave-2 state and that fact is flagged inline.

5) CloudKit. OmniDerm.entitlements declares com.apple.developer.icloud-services = CloudKit + CloudDocuments, container iCloud.com.omni.OmniDerm. Domain/Services/CloudSyncService.swift writes a record type "DermSignals" (recordName "DermUserSignals") to container.privateCloudDatabase with fields: goals (joined string), streak (Int), consistency (Double), updatedAt, provenance. Streak and consistency are computed from SkinHabitLog entries — i.e. they are health-DERIVED, which is squarely consumer health data under RCW 19.373.010's "infer, derive" language. The service's own doc comment "No medical data in CK" is wrong. It is a private-database write (the developer cannot read a user's CloudKit private database), user-initiated via a "Sync Now" button, and the toggle defaults to false in Features/Settings/SettingsView.swift (`@State private var ckEnabled = false`). Also: the hardcoded container id iCloud.com.omni.OmniDerm does not match PRODUCT_BUNDLE_IDENTIFIER legal.prameya.OmniDerm, so CloudKit does not actually provision today (DERM-035).

6) HealthKit. Domain/Services/SkinDataService.swift holds an HKHealthStore and requests READ-ONLY authorization for exactly three types: stepCount, sleepAnalysis, activeEnergyBurned (toShare: [] — no writes), querying the last 7 days for habit correlations computed on device. The Settings toggle defaults OFF. BUT OmniDerm.entitlements requests com.apple.developer.healthkit.access = ["health-records"] (Clinical Health Records) and healthkit.background-delivery, neither of which any shipped feature uses — ISSUES.md DERM-032, a blocker slated for removal.

7) Local storage. SwiftData model Data/Models/SkinHabitLog.swift: date + four booleans (spfMorning, spfReapply, barrier, selfCheck) + a provenance string. UserDefaults: omniDermUserGoals, omniDermRemindersEnabled, selected model id, known-downloaded model ids, and NSURLSessionDownloadTaskResumeData blobs. Keychain via Domain/Core/Security/SecureStore.swift with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly (device-only, not iCloud keychain). Logging is Apple's os.Logger (on-device unified log). No com.apple.developer.default-data-protection entitlement is set (DERM-036).

8) User controls that already exist. Settings has "Export Full Data (JSON)" via ShareLink (appVersion, exportedAt, disclaimer, provenance, all habit logs, resilience snapshot, goals) and "Clear All Local Data", which deletes all SkinHabitLog rows, clears the caches, removes the two UserDefaults keys and cancels pending local notifications. There is NO explicit "delete photos" control — because there is nothing persisted to delete; photos live in memory only.

9) Notifications are local only (UNUserNotificationCenter). Info.plist declares UIBackgroundModes fetch + remote-notification with no aps-environment entitlement — a dormant capability, DERM-033, slated for removal. No push server exists.

10) Tracking. PrivacyInfo.xcprivacy sets NSPrivacyTracking=false and an empty NSPrivacyTrackingDomains. No IDFA, no ATT, no ad or attribution SDK. But it also declares NSPrivacyCollectedDataTypes for HealthFitness and PhotosorVideos, which under Apple's "collect = transmitted off device" definition is not true of photos and is only arguably true of health data because of the CloudKit write (DERM-111).

NET POST-WAVE-2 PICTURE THE POLICY DESCRIBES: skin photos are chosen from the photo library, processed in memory on the device, never written to disk and never uploaded; habit logs and Health data stay on device; the only non-Apple network connection is an HTTPS model-weights download from Hugging Face that carries no user content; iCloud sync is off by default, uses the user's own private database, and is restricted to non-health preferences/UI state; the photo-analysis output sits behind a default-OFF clearance gate so the shipping configuration produces no assessment of a photograph. Three of those (the clearance gate, the CloudKit health-data restriction, and the removal of health-records/background-delivery) are wave-2 changes I could not confirm in the code and are flagged inline in both documents.

## Corrections to prior claims

- FALSE: 'All processing on-device. No data leaves your device.' — shipped user-visible string in Features/Learn/LearnView.swift. TRUTH: the app downloads AI model weights from huggingface.co over HTTPS on first use, and (today) CloudSyncService uploads goals, streak and consistency to CloudKit. User content does not leave the device; the blanket 'no data leaves your device' is untrue and is exactly the kind of overclaim the FTC treats as deceptive.
- FALSE / INCOMPLETE: 'Privacy: All MLX on-device. HealthKit/CloudKit/Reminders user-controlled and optional. No tracking.' — Features/Settings/SettingsView.swift. TRUTH: 'No tracking' is accurate (NSPrivacyTracking=false, empty tracking domains, no ad or analytics SDK, no IDFA). 'All MLX on-device' is accurate for inference but omits that the model files are fetched from Hugging Face over the network. The omission is the problem, not the phrase.
- FALSE: 'No medical data in CK' — doc comment in Domain/Services/CloudSyncService.swift. TRUTH: the record it writes ('DermSignals') carries streak and consistency, both computed from SkinHabitLog skin-care habit entries. Under RCW 19.373.010, data that is inferred or derived from health data is consumer health data. This must be non-health-only after Wave 2, and the comment must be corrected.
- FALSE: 'syncs only lightweight habit signals ... No medical data' framed as privacy-neutral — same file. TRUTH: habit signals in a dermatology app are health-derived. Also note App Review Guideline 5.1.3(ii) flatly prohibits storing personal health information in iCloud, which is why this is a blocker (DERM-031) rather than a judgment call.
- MISLEADING: NSCameraUsageDescription in Info.plist — 'Optional camera access for educational skin photo self-checks and photo diaries ... Images processed locally never uploaded.' TRUTH: no code path uses the camera. There is no AVCapture, AVFoundation capture, or UIImagePicker anywhere in the tree; images come exclusively from the photo library via PhotosPicker. The permission is requested for a feature that does not exist. ('Never uploaded' is itself accurate.)
- UNPROFESSIONAL AND MEANINGLESS TO USERS: 'BLS: customers of dermatologists/skin health pros' appears verbatim inside NSHealthShareUsageDescription and NSPhotoLibraryUsageDescription — the copy iOS shows at the exact moment of consent. TRUTH: these are internal market-research notes that leaked into consent prompts (DERM-006). A purpose string must state the data and the purpose in the user's language. The HealthKit string is also 430+ characters, past what the alert legibly displays.
- FALSE UNDER APPLE'S OWN DEFINITION: PrivacyInfo.xcprivacy declares NSPrivacyCollectedDataTypes for HealthFitness and PhotosorVideos. TRUTH: Apple defines 'collect' as transmitting data off the device. Photos are never transmitted, so PhotosorVideos is wrong. HealthFitness was arguably true only because of the CloudKit write; once that is restricted to non-health data it becomes wrong too. A false privacy label is both an App Review problem and an FTC section 5 problem (DERM-111). Separately, do not let this Apple definition be used to imply Washington's MHMDA does not apply — MHMDA's 'collect' expressly includes inferring and deriving.
- MISLEADING ENTITLEMENT: OmniDerm.entitlements requests com.apple.developer.healthkit.access = ['health-records'] (Clinical Health Records) and healthkit.background-delivery. TRUTH: the only HealthKit code (SkinDataService.requestHealthKitAuthorization) reads exactly three types — stepCount, sleepAnalysis, activeEnergyBurned — read-only, with toShare: []. No feature reads clinical records and no feature uses background delivery. Any policy saying the app may access health records would be false; the entitlement must go (DERM-032).
- NON-FUNCTIONAL AS SHIPPED: CloudSyncService hardcodes CKContainer(identifier: 'iCloud.com.omni.OmniDerm') and the entitlements use the com.omni.* naming, while the Xcode project builds legal.prameya.OmniDerm. TRUTH: CloudKit would not provision and keychain access would fail at runtime (DERM-035). Any claim that sync works today is wrong.
- NOT THIS APP'S: the stray /OmniDent.entitlements at the OmniDerm repo root declares Sign in with Apple, aps-environment, and OmniDent iCloud containers. TRUTH: OmniDerm has no accounts, no sign-in, and no push server. If that file were ever selected by a build configuration it would request capabilities for a different bundle id (DERM-034). No privacy policy for OmniDerm may mention accounts or push.
- DORMANT CAPABILITY: Info.plist declares UIBackgroundModes = fetch + remote-notification. TRUTH: there is no aps-environment entitlement and no push infrastructure; all notifications are local (UNUserNotificationCenter). A policy must not imply server-driven notifications (DERM-033).
- OUT OF SCOPE: the existing shared policy at prameyallc.github.io/edu-app-privacy scopes itself to apps with NO accounts, NO uploads, and NO health or financial data. TRUTH for OmniDerm: no accounts is correct, but the app processes skin images, processes consumer health data, reads Apple Health with permission, and writes to CloudKit. That policy has never been true of OmniDerm and must not be linked from its App Store listing.
- STILL SHIPPING IN THE DEAD TREE: OmniDerm/App/SkinHabitsFeature.swift line 54 still renders 'EDUCATIONAL GATE: Build SPF/barrier/self-check habits (evidence: ~40-50% risk reduction).' TRUTH: that figure was removed from the live tree as an unsubstantiated claim falsely attributed to the AAD; it traces to the Australian Nambour trial, not to the AAD, and generalising it to US consumers is itself an unsubstantiated claim (DERM-001 / DERM-120). It is not a privacy claim, but it is a live FTC exposure sitting in a revivable file and should be deleted with the rest of the dead tree.
- UNQUALIFIED PERFORMANCE IMPLICATION: nothing in the shipped copy tells users that dermatology AI performs worse on darker skin. TRUTH: Daneshjou et al., Sci Adv 2022;8(32):eabq6147 found every evaluated model performed worse on dark skin tones, and no skin-tone-stratified evaluation of the shipped Qwen2-VL model exists (DERM-003). Marketing an unqualified vision feature to all users is an implied claim of uniform performance. Both policies now disclose this.

## Open questions

- FDA CLEARANCE GATE DOES NOT EXIST IN THE CODE I READ. Both policies state that the photo-to-assessment feature is behind a default-off clearance gate. As of the 2026-08-08 tree, Features/Learn/LearnView.swift still contains PhotoSelfCheckEducationView, which runs a Qwen2-VL prompt over a user-picked photo and renders ABCDE observations. Domain/Core/Claims/DermClaimsGate.swift is a copy linter (it flags strings like 'point your camera at'), not a runtime feature switch. Do not publish either policy until the gate ships and defaults off, or the policy is false on its most important claim.
- CLOUDKIT HEALTH-DATA RESTRICTION IS UNCONFIRMED. CloudSyncService.swift currently writes a 'DermSignals' record containing goals, streak and consistency. Streak and consistency are computed from SkinHabitLog entries, so they are derived from health data and are consumer health data under RCW 19.373.010's 'infer, derive' language. The policies say only non-health preferences and UI state sync. Confirm before publishing.
- HEALTH-RECORDS ENTITLEMENT MUST BE REMOVED BEFORE PUBLISHING. OmniDerm.entitlements still requests com.apple.developer.healthkit.access = ['health-records'] plus background-delivery, with no feature using either (DERM-032). The main policy states flatly that the app does not read clinical health records. If the entitlement ships, the binary contradicts the policy and that is both an App Review problem and an FTC section 5 problem.
- Does the camera get used at all? Info.plist declares NSCameraUsageDescription, but there is no AVCapture, AVFoundation, or UIImagePicker code anywhere in the tree — intake is PhotosPicker only. Either remove the camera usage string, or, if Wave 2 adds live capture, tell me so the photo section is rewritten (live capture changes the retention story: a captured image is not yet in the user's photo library, so 'delete it in Photos' would no longer be the right instruction).
- MODEL DOWNLOAD CONSENT. MLXModelPolicy is .unrestricted, so a 1.2 GB vision model can download with no size or cellular prompt (DERM-050). If Wave 2 adds a consent prompt, the Hugging Face section should describe it. If the vision model entry is deleted, the sizes quoted in the policy (420 MB / 1.2 GB) need updating to 420 MB only.
- APP STORE TERRITORIES. The GDPR/UK section is written conditionally. Confirm whether OmniDerm is US-only; if so, that section should be cut to two lines rather than shipped as boilerplate.
- APP STORE AGE RATING. The age-rating questionnaire was still outstanding (DERM-110). The COPPA section asserts the app is not directed to children; make sure the App Store age rating and category (Health & Fitness, per DERM-116) are consistent with that before publishing.
- FILE PROTECTION. No com.apple.developer.default-data-protection entitlement is set (DERM-036). If Wave 2 adds NSFileProtectionComplete, upgrade the Security section to state that stored data is encrypted at rest when the device is locked. Do not state that today.
- PRIVACY MANIFEST RECONCILIATION. PrivacyInfo.xcprivacy declares NSPrivacyCollectedDataTypes for HealthFitness and PhotosorVideos. Under Apple's definition ('collect' = transmitted off device) neither is true once CloudKit is restricted to non-health data and photos remain memory-only. The manifest, the App Store Connect privacy answers and this policy must be made to agree before submission (DERM-111).
- SUPPORT EMAIL RETENTION. The policy says support threads are deleted once resolved. Confirm that is actually the practice at admin@prameya.legal, or I should soften it to a stated retention period.
- MHMDA SCOPE QUESTION FOR COUNSEL (REGULATORY.md OQ-D10): does 'collect' under RCW 19.373 reach purely on-device inference over a photograph of the user's own body? No WA AG guidance or case law was located. The policies deliberately assume YES and are written to comply either way, which is the safe posture — but counsel should confirm rather than rely on my assumption.
- NEVADA SECTION NUMBERS. SB 370 (2023) added new sections to NRS ch. 603A effective 2024-03-31. I cited the bill rather than pinning specific NRS section numbers I could not verify in this session. If you want section-level citations, have counsel supply them rather than letting me guess.
