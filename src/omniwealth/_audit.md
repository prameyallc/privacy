# OmniWealth — data-flow audit

AUDIT BASIS: read /Users/sbkoth/work/Omni/OmniWealth/docs/REGULATORY.md, ISSUES.md, README.md, docs/APP_STORE.md, PrivacyInfo.xcprivacy, OmniWealth.entitlements (+ .bak), Info.plist, Package.swift/Package.resolved, and every Swift source in the shipping Xcode target. NOTE ON TREES: the repo has two parallel source trees (ISSUES WEALTH-010). OmniWealth.xcodeproj compiles root App/, Domain/, Features/, Data/, DesignSystem/ plus OmniWealth/AppFeatures, OmniWealth/Core, OmniWealth/DesignSystem, OmniWealth/MLX, and signs with the ROOT OmniWealth.entitlements and ROOT PrivacyInfo.xcprivacy. The stripped-down copies under OmniWealth/ (no HealthKit, no CloudKit, no collected-data-types) are the SPM canary target, not the app. Findings below are for the Xcode target = the thing that ships.

NETWORK EGRESS — exactly one destination. OmniWealth.entitlements grants com.apple.security.network.client. Info.plist sets NSAppTransportSecurity/NSAllowsArbitraryLoads = false. The only outbound traffic in the tree is Hugging Face model-weight download: Package.swift links huggingface/swift-huggingface 0.9.0 and swift-transformers 1.3.3; OmniWealth/MLX/Download/{HubDownloaderBridge,RobustDownloader,ResilientResolve}.swift call HubClient.downloadSnapshot(of:revision:matching:). HubClient.defaultHost is https://huggingface.co (.build/checkouts/swift-huggingface/Sources/HuggingFace/Hub/HubClient.swift:53). Repos requested come from Domain/AI/OmniWealthCatalog.swift: LLMRegistry.qwen3_0_6b_4bit (~420 MB, text) and mlx-community/Qwen2-VL-2B-Instruct-4bit (~1.2 GB, vision+text). The download is user-initiated: MainTabView.downloadAndLoad() is wired to the "Download & Load" control in SettingsView -> OmniMLXSettingsView. No HF token is configured, so requests are unauthenticated. Background URLSession config exists in RobustDownloader for resume across launches. WHAT IS SENT: repo id, revision ("main"), file paths, HTTP Range/If-Range headers, plus the unavoidable IP address and user agent. NO user content is sent. Grep found zero occurrences of AdMob/GoogleMobileAds, AdSupport, ATT/IDFA, Firebase, analytics, crash reporting, ASAuthorization/Sign in with Apple (AuthenticationServices.framework is linked in the pbxproj but never imported or used), StoreKit, or any Prameya-operated endpoint. Transitive deps (swift-nio, EventSource, swift-crypto, yyjson, swift-jinja, swift-syntax, swift-collections, swift-atomics, swift-numerics, swift-system, swift-asn1, mlx-swift, mlx-swift-lm) are transport/compute libraries; a URL grep over swift-transformers and EventSource sources found only documentation links, no telemetry hosts. ISSUES WEALTH-021 correctly notes a formal per-dependency telemetry audit has not been recorded — that remains open.

ON-DEVICE STORAGE. App/OmniWealthApp.swift builds two SwiftData containers in Application Support: wealth-default.store (WealthHabitLog, BudgetEntry, StatementScan, WealthTrajectorySnapshot, WealthProfile) and wealth-sync.store (WealthProfile, WealthHabitLog). CRITICAL: BOTH are created with ModelConfiguration(..., cloudKitDatabase: .none). Data/Models/WealthModels.swift shows the fields: habit booleans + free-text notes; budget date/category/amount/isExpense/note; profile monthlyIncome/targetMonthlyContribution/riskTolerance/goals. UserDefaults holds app.appearance, mlxSelectedModelID, the known-downloaded model list, and MLX resume-data blobs. OmniWealth/Core/Security/SecureStore.swift (Keychain, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly) is DEAD CODE — no call sites in the app target.

iCloud — DOCS ARE WRONG, CODE IS THE TRUTH. REGULATORY.md §5.1/§6.2, ISSUES WEALTH-005/WEALTH-062 and README all assert "CloudKit sync is enabled by default and syncs habit/profile data to iCloud." That is not what the shipping code does. Domain/Services/CloudSyncService.swift declares isEnabled = true, but the actor is NEVER INSTANTIATED OR REFERENCED anywhere outside its own file (grep confirmed), and the only CloudKit API it would ever call is CKContainer.accountStatus() — a status probe, not a data write. Combined with cloudKitDatabase: .none on both containers, NO USER DATA REACHES iCLOUD IN THE CURRENT BUILD. The entitlements do grant iCloud (CloudKit + CloudDocuments, container iCloud.com.omni.OmniWealth) — an unused capability, not an active flow.

HEALTHKIT — ENTITLED, ZERO CODE, FABRICATED OUTPUT. Root OmniWealth.entitlements requests com.apple.developer.healthkit, com.apple.developer.healthkit.access = ["health-records"] (FHIR clinical medical records), and healthkit.background-delivery. Info.plist carries NSHealthShareUsageDescription promising steps/sleep/activity reads. There is no HKHealthStore, no HealthKit import, anywhere in the tree. App/RootView.swift:32 calls appDataService.integrateHealthKitInsights(steps: 7200, sleepHours: 7.0) with hardcoded literals, and AppDataService renders "HK context (educational): steps=7200, sleep=7.0h" to the user as if it came from Health. This is WEALTH-001, the repo's top blocker, slated for removal in wave 2.

NO BANK CONNECTIONS. Confirmed by code: no Plaid, no aggregator, no OAuth, no financial-institution SDK, no account-linking UI. REGULATORY.md §5.2 reaches the same conclusion (CFPB 12 CFR Part 1033 attaches to data providers and authorised third parties; OmniWealth is neither).

NO CAMERA / PHOTOS / DOCUMENT IMPORT IN THE SHIPPING BUILD. Grep for PHPicker, PhotosUI, PhotosPicker, UIImagePickerController, AVCapture, VisionKit, fileImporter, DocumentPicker returned nothing. The StatementScan @Model and the Qwen2-VL vision catalog entry exist, and OmniWealth/MLX/AnalysisImage.swift can decode images, but there is no user-facing capture or import path and AppDataService.saveStatementScan has no caller. The entitlement com.apple.security.files.user-selected.read-only is granted and unused. So the shipped app cannot ingest a statement today, even though WealthHomeView copy claims it gives "feedback from your logs or uploaded statements."

NOTIFICATIONS. AppDataService.scheduleReminderIfNeeded logs a line and returns (WEALTH-006). The app never asks for notification permission and schedules nothing. Info.plist declares UIBackgroundModes = [fetch] with no background-fetch implementation.

ACCOUNTS / ADS / CHILDREN. No sign-in, no user identifier of any kind, no ad SDK, no tracking. NSPrivacyTracking = false. General-audience adult personal-finance product.

PRIVACY MANIFEST IS FALSE AND INVALID. Root PrivacyInfo.xcprivacy declares NSPrivacyCollectedDataTypeHealth AND NSPrivacyCollectedDataTypeSensitive for on-device budget/habit logs with purpose NSPrivacyCollectedDataTypePurposeHealth, and declares NSPrivacyAccessedAPICategoryHealthKit and NSPrivacyAccessedAPICategoryCloudKit — neither of which is a valid required-reason category (the closed list is FileTimestamp, SystemBootTime, DiskSpace, ActiveKeyboards, UserDefaults). Nothing is transmitted off device for developer access, so NSPrivacyCollectedDataTypes should be empty. This is WEALTH-004.

NET: post-wave-2, the honest description is — user-entered financial information stays on the device; the only thing that leaves is a model-weight request to Hugging Face; Prameya operates no server, receives no user content, and holds no user database; the app is educational and gives no personalised financial advice.

## Corrections to prior claims

- PrivacyInfo.xcprivacy (root) declares budget/habit logs as NSPrivacyCollectedDataTypeHealth. FALSE — budgeting and contribution logs are FINANCIAL data, not health data. Correct: they are financial data, they are stored only on device, and nothing is transmitted off device for developer access, so NSPrivacyCollectedDataTypes should be an EMPTY ARRAY. The false 'health' label also drags the app toward Washington MHMDA and Apple Guideline 5.1.3(ii) for no reason.
- PrivacyInfo.xcprivacy also declares NSPrivacyCollectedDataTypeSensitive with purpose NSPrivacyCollectedDataTypePurposeHealth. FALSE on both counts — nothing is collected in Apple's transmission sense, and the purpose is not health. Delete the entry.
- PrivacyInfo.xcprivacy declares NSPrivacyAccessedAPICategoryHealthKit and NSPrivacyAccessedAPICategoryCloudKit. Neither is a valid required-reason API category (the closed list is FileTimestamp, SystemBootTime, DiskSpace, ActiveKeyboards, UserDefaults). Correct: delete both; an invalid manifest is auto-rejected by App Store Connect.
- Info.plist NSHealthShareUsageDescription states 'OmniWealth optionally accesses HealthKit (steps, sleep, activity) with your explicit permission.' FALSE — there is no HKHealthStore, no HealthKit import, and no Health code anywhere in the tree. Correct: the app has no Health integration; the string must be deleted.
- OmniWealth.entitlements requests com.apple.developer.healthkit, com.apple.developer.healthkit.access = ['health-records'], and com.apple.developer.healthkit.background-delivery. Requesting read access to a user's FHIR-backed clinical medical records in a budgeting app is unjustifiable and unused. Correct: the app needs no HealthKit entitlement of any kind; all three keys must be removed.
- The app displays 'HK context (educational): steps=7200, sleep=7.0h' as though it came from Health. FALSE — App/RootView.swift:32 passes hardcoded literals to AppDataService.integrateHealthKitInsights. No device was ever queried and the user granted nothing. Correct: this is fabricated data shown as fact and must be removed, not relabelled.
- README.md, docs/REGULATORY.md §5.1/§6.2 and ISSUES.md WEALTH-005/WEALTH-062 all state that 'CloudKit sync is enabled by default and syncs habit/profile data to iCloud.' NOT TRUE OF THE SHIPPING CODE. App/OmniWealthApp.swift creates BOTH ModelContainers with cloudKitDatabase: .none, and CloudSyncService is never instantiated or referenced outside its own file; its only CloudKit call is CKContainer.accountStatus(), a status probe. Correct: no user data reaches iCloud in the current build. The iCloud entitlements are present but unused. Trust the code over the docs, and fix the docs.
- The entitlements grant com.apple.developer.icloud-services = [CloudKit, CloudDocuments]. CloudDocuments is entirely unused — nothing in the app writes an iCloud document. Correct: remove it; an unused capability is still a capability a reviewer will ask about.
- README.md's 'Product notes' historically described reminders as implemented. FALSE — AppDataService.scheduleReminderIfNeeded logs a line and returns. The app never requests notification permission and schedules nothing. Correct: no notifications are sent.
- Info.plist declares UIBackgroundModes = ['fetch'] with no background-fetch implementation anywhere. Correct: remove it, or implement it. Declaring a background mode the app does not use is both a Guideline 2.5.4 rejection risk and a misstatement about what the app does when you are not looking at it.
- WealthHomeView's shipped disclaimer copy says OmniWealth 'provides on-device educational feedback from your logs or uploaded statements.' NOT TRUE of the shipping build — there is no camera, photo picker, document picker, or fileImporter anywhere in the app, and AppDataService.saveStatementScan has no caller. Correct: the app cannot ingest a statement. Any privacy policy claiming statement processing would be describing a feature that does not exist.
- The entitlement com.apple.security.files.user-selected.read-only is granted and unused (no file picker exists). Correct: remove it until an import feature actually ships.
- OmniWealthCatalog declares MLXModelPolicy(requiresConsentAboveMB: 100, hasDownloadConsent: { true }). The consent gate is hardcoded to approve, so the size threshold is decorative. Correct: either present a real consent sheet naming the model and its size, or stop describing the app as having a download-consent policy. (The download itself is still user-initiated from the Settings button — that part is accurate.)
- PrivacyInfo.xcprivacy's trailing comment describes the app as 'Pure on-device MLX... No cloud processing of logs or statements' and the portfolio baseline assumed 'no networking / no third-party dependencies.' The on-device-inference half is TRUE and worth stating. The 'no networking' half is FALSE for this app: OmniWealth.entitlements grants com.apple.security.network.client and OmniWealth/MLX/Download/ fetches model weights from huggingface.co at runtime via swift-huggingface (HubClient.defaultHost = https://huggingface.co). Correct: the app connects to Hugging Face to download model files; user content is never sent; inference then runs locally.
- The existing shared policy at prameyallc.github.io/edu-app-privacy scopes itself to apps with no accounts, no uploads, and no health or financial data. It does not describe OmniWealth: the app stores user-entered financial information (income, contributions, budget amounts and categories, goals) locally. Correct: OmniWealth needs its own policy — this one — and the shared policy must stop being linked from OmniWealth's App Store listing.
- Any prior statement or implication that OmniWealth connects to a bank, brokerage, or data aggregator would be false; equally, any implication that it offers advisory or portfolio services would be false. Correct: there is no account linking of any kind in the code (no Plaid, no OAuth, no institution SDK), and the product is educational only. This also matters outside privacy — it is the basis of the app's posture under the Investment Advisers Act.
- OmniWealth/Core/Security/SecureStore.swift (Keychain wrapper) and the keychain-access-groups entitlement exist but have no call sites in the app target. Correct: do not describe the app as storing anything in the Keychain — it does not.
- SettingsView copy says 'Export available in future.' AppDataService.exportWealthResilienceSummary exists but is unreachable from the shipping UI. Correct: no export exists today; do not describe one.
- docs/REGULATORY.md's own §6.2 heading treats CloudKit as an active deviation from the portfolio baseline. Given the code (cloudKitDatabase: .none, CloudSyncService unreferenced), the accurate deviation list for OmniWealth is: (1) network client + Hugging Face model download — REAL; (2) iCloud entitlements — GRANTED BUT UNUSED; (3) HealthKit entitlements — GRANTED BUT UNUSED, with fabricated output; (4) notification scheduling — NOT IMPLEMENTED.

## Open questions

- Distribution territories: is OmniWealth released US-only or worldwide? The GDPR/UK GDPR section is written for worldwide availability and should be cut or kept accordingly.
- Will the unused iCloud entitlements (CloudKit + CloudDocuments, container iCloud.com.omni.OmniWealth) actually be removed in wave 2, or will an opt-in sync ship? If sync ships, the policy needs the exact list of fields that sync before publication.
- Will the HealthKit entitlements (healthkit, healthkit.access: health-records, healthkit.background-delivery), the NSHealthShareUsageDescription string, and the hardcoded steps=7200/sleep=7.0 output actually be gone from the submitted binary? Publishing 'we do not read Apple Health' against a binary that still ships those entitlements would be the exact kind of misdescription this exercise exists to prevent.
- Will the vision/statement-scan feature ship? The Qwen2-VL entry sits in the model catalogue and the StatementScan model exists, but no capture or import path does. If it ships, the policy needs a photos/files section and the App Store label needs updating.
- Does an in-app 'delete all my data' control ship in wave 2? Today there is no delete UI at all — not even per-entry — so the 'delete individual entries in the app' line in the policy is currently aspirational and needs either code or rewording.
- Confirm the Hugging Face requests remain unauthenticated in the shipped build (no HF token configured anywhere, including via HF_ENDPOINT or environment/token-file discovery in swift-huggingface).
- Per-dependency telemetry audit (ISSUES WEALTH-021) has not been formally recorded. Sixteen transitive packages resolve, including swift-nio and EventSource. A URL grep found no telemetry hosts, but a documented audit is needed before answering 'Data Not Collected' on the App Store privacy questionnaire.
- Does the app-side model download check free disk space? If RobustDownloader calls volumeAvailableCapacity or equivalent, NSPrivacyAccessedAPICategoryDiskSpace with reason E174.1 must be declared (WEALTH-022). Grep found no such call in the current tree — confirm after wave 2 edits.
- Will NSFileProtectionComplete (or CompleteUnlessOpen) be set on the SwiftData store? The security section is deliberately written to the OS default until this is confirmed.
- Two parallel source trees still exist (WEALTH-010). The stripped OmniWealth/ copies of Info.plist, entitlements and PrivacyInfo.xcprivacy differ materially from the root ones the Xcode target signs with. Whoever verifies this policy must check the ROOT files, not the SPM-tree copies.
- App Store age rating and category: confirm the app is not placed in the Kids Category and 'Medical or wellness topics' is answered No (true only once HealthKit is removed).
- Is the effective date of 2026-08-08 correct given wave 2 is still in flight? If the app ships later, the date should match the state of the binary being described, or the TO VERIFY notes must be resolved first.
