# OmniLex — data-flow audit

AUDIT OF /Users/sbkoth/work/Omni/OmniLex, code read on 2026-08-08. Findings are from source, not docs; where docs and code disagree I trusted code.

ACCOUNTS / BACKEND: None. No sign-in of any kind (no ASAuthorization / Sign in with Apple, no StoreKit, no account API). Prameya operates no server for this app. No user-profile database. No analytics, ads, crash-reporting or telemetry SDK anywhere (no Firebase/Sentry/Crashlytics/GoogleMobileAds). Logging is Apple OSLog only (Core/OmniCore/Logging/OmniLogger.swift, subsystem legal.prameya.OmniLex) and stays on device.

DOCUMENT IMPORT: SwiftUI .fileImporter in Features/Home/Views/HomeView.swift:120 and Features/Vault/Views/VaultView.swift:80, allowedContentTypes [.pdf, .plainText, .rtf, .image]. macOS entitlement com.apple.security.files.user-selected.read-only/read-write. Security-scoped bookmarks (Core/Utilities/SecurityScopedBookmark.swift) persist a reference to the user-chosen file. No PHPicker/PhotosUI and no AVCaptureDevice anywhere in the sources — the app cannot read the photo library or use the camera, despite INFOPLIST_KEY_NSCameraUsageDescription and INFOPLIST_KEY_NSPhotoLibraryUsageDescription being set in OmniLex.xcodeproj/project.pbxproj:336,340 (ISSUES.md LEX-005 marks these for removal).

TEXT EXTRACTION: Core/Utilities/TextExtractionService.swift uses PDFKit for text PDFs and Apple Vision (VNRecognizeTextRequest) OCR for scanned PDFs and images. Both are on-device Apple frameworks. No cloud OCR.

STORAGE: SwiftData local store, ModelConfiguration(isStoredInMemoryOnly: false) in OmniLex/OmniLexApp.swift:43. Models: Document (holds title, url, bookmarkData, full textContent, summary, tags, userNotes), Risk, ChatMessage, Template, KnowledgeNote, DocumentChunk. NO CloudKit: no CKContainer, no cloudKitDatabase in the ModelConfiguration, no iCloud entitlement in any of the three .entitlements files. Nothing syncs. Note ISSUES.md LEX-035: no explicit NSFileProtectionComplete / FileProtectionType is set anywhere — the store relies on default OS data protection only. Keychain wrapper exists (Core/OmniCore/Security/SecureStore.swift, service "com.omni.secure" — LEX-036 flags the generic identifier). UserDefaults holds preferences (showLegalDisclaimerOnLaunch, defaultRiskThreshold), the selected model ID, and MLX download resume-data blobs (Core/MLX/Download/RobustDownloader.swift:162-176).

AI: fully on-device MLX inference (Core/MLX/Inference/MLXLLMClient.swift). Catalog in Core/AI/OmniLexCatalog.swift = Qwen3 0.6B/1.7B/4B 4-bit and Phi-2 4-bit, 420 MB–2.5 GB. Semantic search uses Apple NaturalLanguage NLEmbedding on-device (Core/AI/EmbeddingActor.swift). The ~3,649-file legal skill pack is bundled in Resources/LegalSkills, loaded from the bundle, no runtime fetch (verified: no URLSession/http in Core/AI/Skills).

NETWORK EGRESS — exactly two paths exist in the shipping tree:
1. Hugging Face model downloads. Core/MLX/Download/HubDownloaderBridge.swift and RobustDownloader.swift use the swift-huggingface HubClient; RobustDownloader.swift:8 documents pulls via the Xet/CAS CDN (cas-bridge.xethub). Weights + tokenizer only. No user content is sent. Info.plist sets NSAppTransportSecurity NSAllowsArbitraryLoads=false (HTTPS only); macOS entitlement com.apple.security.network.client.
2. THE DEVIATION — web search, still present as of this audit. Core/Utilities/WebSearchService.swift:30 builds "https://api.duckduckgo.com/?q=...&format=json..." and Features/Vault/Views/CaseStorySheet.swift:350,364 constructs WebSearchService() and calls it with queries built by makeSearchQueries(from: facts, documentTitle: document.title) — i.e. model-extracted facts from the user's document AND the document title leave the device as URL query parameters to a third party. This matches ISSUES.md LEX-001 and docs/REGULATORY.md §2 exactly. Wave 2 removes it; git log shows the tree is still at wave 1 ("Portfolio hardening wave 1"), and WebSearchService.swift and the CaseStorySheet call site are both still in place. The policy is written to the post-removal state and every dependent sentence is flagged TO VERIFY BEFORE PUBLISHING.

OTHER LOCAL-ONLY FEATURES: Read Aloud via AVSpeechSynthesizer (Core/Utilities/SpeechSynthesizerService.swift) — OS speech, no network call by the app. PDF risk report export via .fileExporter (Features/Reports/Views/ReportsView.swift:30, Features/Vault/Views/DocumentDetailView.swift:125) — user picks the destination; nothing is uploaded.

HEALTH DATA: none. No HealthKit, no HKHealthStore, no health fields in the schema. (The single "HealthKit" grep hit is a code comment in a vendored design-system file, Core/DesignSystem/Shared/OH/ProgressAndToast.swift:8, describing a different app.) So no My Health My Data / Nevada SB 370 consumer-health policy is owed — healthPolicyMarkdown returned empty.

PRIVACY MANIFEST: OmniLex/PrivacyInfo.xcprivacy declares NSPrivacyTracking=false, empty tracking domains, empty NSPrivacyCollectedDataTypes, and required-reason APIs FileTimestamp (C617.1) + UserDefaults (CA92.1). ## Corrections to prior claims

- FALSE: OmniLex/ContentView.swift:297 tells every new user on the first-run screen '100% on-device - No data leaves your device.' ACCURATE: your documents and everything derived from them stay on your device, but the app does connect to Hugging Face to download AI model weights. That is data leaving and arriving. And until the wave-2 removal lands, document-derived search queries and the document title are also sent to api.duckduckgo.com.
- FALSE: project.pbxproj:338, NSHumanReadableCopyright — 'All processing happens 100% on-device. No data is sent to any server.' ACCURATE: AI inference, OCR, text extraction and semantic search all run on-device. The app does contact a server — Hugging Face — to fetch model weights, and today it also contacts a search API.
- FALSE: OmniLex/PrivacyInfo.xcprivacy header comment — 'OmniLex is a 100% on-device, privacy-first legal AI companion. No data is ever sent to any server.' ACCURATE: same correction. This one matters more than the others because it sits in the file Apple parses, next to an empty NSPrivacyCollectedDataTypes array, and it is the document a reviewer reads as the developer's own privacy attestation.
- FALSE: project.pbxproj:340, NSPhotoLibraryUsageDescription — 'OmniLex needs access to photos and images you select ... Nothing is uploaded.' ACCURATE: the app has no photo-library access at all. There is no PHPicker or PhotosUI usage anywhere in the sources. Images are imported through the standard file picker. The permission string requests access the app never uses, which reads as over-collection.
- FALSE: project.pbxproj:336, NSCameraUsageDescription — 'OmniLex can use the camera to capture document pages.' ACCURATE: the app cannot use the camera. There is no AVCapture code in the repo. This describes a feature that does not exist.
- FALSE: project.pbxproj:339, NSLocalNetworkUsageDescription — 'OmniLex can discover and import documents from other devices on your local network ... No data leaves your device.' ACCURATE: there is no local-network discovery code in the repo. The feature does not exist, and the sentence appended to it repeats the false absolute claim.
- FALSE: PrivacyInfo.xcprivacy declares NSPrivacyCollectedDataTypes as an empty array with the comment 'We collect ZERO data. Intentionally empty. No data leaves the device.' ACCURATE as of the shipping build: 'Data Not Collected' cannot be asserted while document-derived queries go to a third-party search API, because Apple's own definition of collection turns on third-party retention beyond real-time servicing, and that retention has not been analysed. Post-wave-2 the label answer is likely defensible, but the justification is 'no user content is transmitted,' not 'no network access exists.'
- FALSE: CHANGELOG.md line 14 describes Case Story as having a 'Strong privacy warning (only local facts are searched).' ACCURATE: model-extracted facts from the user's document AND the document title were sent to a third party as URL query parameters. Characterising that as 'only local facts are searched' inverts what happened — the facts were extracted locally and then transmitted. A screen-local caveat also does not cure a contradictory headline claim made at first run.
- MISLEADING: Features/Vault/Views/CaseStorySheet.swift:105 — 'Key facts are extracted locally from your document first. Only those facts are used to craft public web searches.' ACCURATE: this is technically true but presents a confidentiality-relevant disclosure as a reassurance. For an app whose users are lawyers holding privileged material, the correct framing was that content derived from a client document is disclosed to a third party.
- OUT OF SCOPE: the existing shared policy at prameyallc.github.io/edu-app-privacy scopes itself to apps with no accounts, no uploads and no health or financial data, and asserts no network access. OmniLex has no accounts and no health or financial data, so those parts hold — but it does have document import and it does make network requests for model downloads. That policy has never been accurate for this app and must not be the linked policy for it.
- INCOMPLETE: README.md line 14 says 'Fully on-device inference with MLX (models download from Hugging Face when you choose).' This one is actually correct and is the model for how the claim should be phrased everywhere else — inference is on-device, downloads are disclosed. The problem is that the app's own first-run screen and Info.plist strings say something stronger and false. Align the app to the README, not the other way round.
- UNSOURCED ADVERTISING: README.md line 7 asserts BLS employment and wage figures with no source or retrieval date, framed around the size of the market. Not a privacy claim, but it is public advertising copy carrying an unsubstantiated quantitative assertion, and it should carry a source and date or be deleted (ISSUES.md LEX-052).
- OVERSTATED: Core/AI/EmbeddingActor.swift header comment says 'All processing stays 100% on-device.' For embeddings specifically this is true. Flagged only because the same phrase is used elsewhere as an app-wide claim where it is not true; the file-level comment should be scoped so it is not later copied into user-facing copy.

## Open questions

- BLOCKING: the DuckDuckGo egress is still in the source tree. Core/Utilities/WebSearchService.swift:30 and Features/Vault/Views/CaseStorySheet.swift:350,364 were both present at audit time on 2026-08-08. This policy states that path has been removed. Do not publish until the removal is merged and verified in the shipping build.
- BLOCKING: five in-app strings still assert the false absolute claim and must be rewritten to match this policy before publication — OmniLex/ContentView.swift:297 ('100% on-device - No data leaves your device'), project.pbxproj:338 NSHumanReadableCopyright, project.pbxproj:339 NSLocalNetworkUsageDescription, project.pbxproj:340 NSPhotoLibraryUsageDescription, and the header comment in OmniLex/PrivacyInfo.xcprivacy. Even post-wave-2 these are wrong, because the model download is still network access.
- Confirm the unused camera and photo-library purpose strings are removed (ISSUES.md LEX-005). The policy says the app does not use the camera or photo library, which is true of the code but contradicted by the declared permissions. A reviewer comparing the two will see a conflict.
- Confirm the exact set of network hosts contacted during a model download. The code path goes through swift-huggingface HubClient and RobustDownloader.swift references the Xet/CAS CDN (cas-bridge.xethub). If the shipping build hits hosts other than huggingface.co, the policy should name them, and the App Store 'significant change' log (LEX-042) should record them.
- Confirm App Store territories. The GDPR/UK GDPR section is written for availability outside the US; if launch is US-only it can be trimmed, and if it is worldwide it should stay as written.
- Decide whether an explicit file-protection class will be set on the SwiftData store before launch (ISSUES.md LEX-035). The policy currently says the app adds no encryption layer of its own and relies on device encryption. If NSFileProtectionComplete lands, that paragraph should be tightened; if it does not, leave the honest version in place.
- Confirm the NSLocalNetworkUsageDescription string is removed entirely. There is no local-network discovery code in the repo, so the permission is both unused and describes a feature that does not exist.
- Confirm whether NSPrivacyAccessedAPICategoryDiskSpace must be added to PrivacyInfo.xcprivacy for the model download path (ISSUES.md LEX-016), and audit each SPM dependency for its own privacy manifest (LEX-017). Neither changes this policy text, but both affect whether the App Store submission's privacy disclosures are complete.
- Have counsel confirm the Florida Bar Ethics Opinion 24-1 characterisation in the 'If you are a lawyer' section. The repo verified that opinion verbatim, so the reference is safe, but the inference drawn from it (that no third-party disclosure occurs post-wave-2) should be signed off by a human.
- ABA Formal Opinion 512 is deliberately not cited anywhere in this policy. docs/REGULATORY.md OQ-008 records that its primary PDF was never opened (HTTP 403). If a human reads it and it supports a stronger or more specific statement to professional users, that can be added later — but nothing from it should be quoted until then.
- Confirm what Apple reports to Prameya as a developer. The policy says 'anonymous, aggregated App Store sales and crash statistics.' If crash reporting is disabled or Apple's developer-facing data differs, adjust that table row.
